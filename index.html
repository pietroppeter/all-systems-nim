T-10 · THE PHRASECabin pressure go

FREEDOM 7Cabin pressure go.
Fuel system go.
Oxygen go.
All systems go.
Alan Shepard, Mercury-Redstone 3, 5 May 1961, as retold by Grammarist and phrases.org.uk, which credit the flight transcript. The Spacelog transcript of the flight is the place to check the exact words before a slide. Not to be mixed up with "A-OK", which NASA's PAO John "Shorty" Powers attributed to Shepard and the tapes later showed he never said.

"All systems go" means every check is done and you can proceed without delay. It comes from the countdowns of the American space program, and it left aerospace to become everyday language for launches of any kind.

It fits this talk three times over:

  1. A launch. FOSDEM 2027 has a brand new devroom for non-mainstream systems languages, and Nim is named in its call. There is no Nim devroom in the 2027 list, so this room is where Nim lives this year.
  2. A poll of systems. A systems language is many systems working together: memory, compiler, backends, interop. Mission control polls each console in turn, and a talk can do the same. Each console is one capability, a demo and a verdict.
  3. Honesty. A console can answer no-go, or call a hold. The scientific Nim talk had "rocks ahead" at the end of each island; here the same honesty has a better name.

Title: All Systems Nim. The pun works when read aloud ("all systems go" with one sound changed) and says the thesis: every system is there, and it is Nim all the way down.

T-07 · SYSTEMS THINKINGWhat is a system, anyway?

The prompt for this talk asks it directly: what is systems thinking, after all? Three answers, each good for one slide.

The 1998 split. In "Scripting: Higher Level Programming for the 21st Century" (IEEE Computer, 1998), John Ousterhout split languages in two: system programming languages (C, C++, Java), typed and compiled, for building data structures and algorithms from scratch; and scripting languages (Tcl, Perl, Python), for gluing components together quickly. You pick one side and pay its price. Most "non-mainstream systems languages" in this devroom are attempts to refuse that choice. Nim's tagline says it plainly: a statically typed compiled systems language with concepts from Python, Ada and Modula, aiming to be efficient, expressive, elegant.

The systems-thinking definition. Donella Meadows, in Thinking in Systems: a system is a set of elements, interconnected so that together they achieve a purpose. Look at a language that way and the question changes. Not "can it touch the metal?" but "how do its parts work together?" In Nim the macros, the type system, the destructors and the backends are not separate features. A macro writes code the type checker checks, which the destructors manage, which any backend can emit. {.polarsExpr.} in nanuq-more is a good example: one macro turns a plain Nim proc into a C ABI function with Arrow buffers, and on the JS backend the same macro does nothing, so the module runs in a browser too.

The human in the loop. The part of a system people forget is the operator. Cognitive load is a systems property: a language that fits in your head lets you hold more of the rest of the system in it. The 2026 version of this argument has a new operator: the coding agent. A language with little syntax, one obvious way to build, readable code and a fast, strict compiler gives an agent the same thing it gives a human: short feedback loops and fewer places to be wrong. Most of the experiments above were written that way.

The talk's thesis, in one sentence:

Nim is a systems language because its parts form a system: low-level control, a high ceiling and a low cognitive load, held together by a compiler you can program. That is why it is good at kernels and at word puzzles.

T-06 · THE CONSOLESThe poll, console by console

This is the material for the main body of the recommended talk. Each console is one capability, with one community example, one example from the recent experiments, and a hold where there is one. A couple of consoles have code that ran when this page was built.

BOOSTERBare metal

Nim compiles to C (or C++, or Objective-C) and then to machine code with the C compiler you already trust. No virtual machine, no mandatory runtime, binaries in the tens of kilobytes. You can turn the GC off, write ptr and cast, and target anything with a C toolchain.

Community: Fusion OS boots on x86-64; Ratel runs on AVR microcontrollers; INGCHIPS lists Nim in its BLE SDK. Lab: Playdate games through playdate-nim.

EECOMLife support

Since Nim 2.0 the default memory management is ORC: reference counting with move semantics and a cycle collector, so memory is freed at a predictable point, with no stop-the-world pauses. You can write your own =destroy, =copy and =sink hooks. nanuq uses them to own objects that live on the Rust heap:

proc `=destroy`(x: DataFrameObj) =
  if x.raw != nil: nq_df_free(x.raw)

proc `=copy`(a: var DataFrameObj, b: DataFrameObj) {.error.}   # no accidental copies

That is RAII across a language boundary, in three lines. Community: Nimbus runs an Ethereum node on a Raspberry Pi.

ORC's cycle collector and multithreading took years to settle; older libraries and tutorials still assume refc.
GUIDOGuidance

Templates, hygienic macros over the typed AST, and a VM that runs ordinary Nim at compile time. Libraries grow their own syntax without a separate code generator. In nanuq, a dataframe is a block:

let bears = newDataFrame:
  name: ["Nanuq", "Siku", "Ursa", "Kallik"]
  island: ["Svalbard", "Svalbard", "Wrangel", "Wrangel"]
  kg: [420, 95, 380, nil]                # nil is a missing value

Below, a macro written for this page runs the poll. The strings are put together by the compiler; the program only prints them.

import std/macros

func spoken(id: string): string =
  ## cabinPressure -> "Cabin pressure"
  for i, ch in id:
    if ch.isUpperAscii: result.add ' '
    result.add(if i == 0: ch.toUpperAscii else: ch.toLowerAscii)

macro poll(systems: varargs[untyped]): untyped =
  result = newStmtList()
  for s in systems:
    let line = spoken(s.strVal) & " go."   # runs inside the compiler
    result.add quote do: echo `line`
  result.add quote do: echo "All systems go."

poll cabinPressure, fuelSystem, oxygen
Cabin pressure go.
Fuel system go.
Oxygen go.
All systems go.
The macro's output, as the compiler sees it, is just echo "Cabin pressure go." three times and a last line. Community: owlkettle builds GTK 4 apps from a declarative macro DSL; Karax does the same for the web.
FIDOFlight dynamics

The same source compiles to C, C++, Objective-C and JavaScript, and NimScript runs it in the compiler's VM. That is not a gimmick for the web: it is how cadero draws its plans natively and shows a 3D viewer in the browser from the same model, how zogyn tests its drag engine natively and ships it to the browser unchanged, and how the board at the top of this page works.

nim c   -d:release app.nim     # C, then your C compiler
nim cpp app.nim                # C++: talk to C++ libraries, Unreal, Qt
nim objc app.nim               # Objective-C: talk to Apple frameworks
nim js  app.nim                # JavaScript: the browser
nim e   build.nims             # NimScript: the compiler's VM
The JS backend is a different world: no threads, no C FFI, and some stdlib modules don't exist there.
RETRODocking

Nim speaks the C ABI in both directions. importc calls anything with a C interface, including Rust that exports one: that is all of nanuq. exportc and --app:lib go the other way: nanuq-more builds a shared library that Python Polars loads as a plugin, from plain Nim procs:

proc isoweek*(d: Date32): IsoWeek {.polarsExpr.} =
  ...   # plain Nim; the pragma also exports it to Polars

Community: nimpy (Python both ways), godot-nim, NimForUE, wrappers generated by Futhark from C headers.

nanuq's Rust half is a ~286 MB static library (53 MB download). Interop is easy; distribution is the hard part. nanuqy is the experiment to drop it.
INCOCompiler

The compiler is a library and a platform: NimScript for build files, hot code reloading (each module a shared library, globals survive reloads), and incremental compilation in Nim 2.4. cicak puts the last two together to try a real REPL: each input becomes a module, loaded into a live process. Nimony, the next compiler, works on NIF, a text format for the compiler's intermediate code that other tools can read and write.

Hot code reloading is rough (main module not reloadable, leaks under ORC, tested only without threads); 2.4.0 shipped without a tool that IC needs. Nimony means a transition ahead.
SURGEONCrew health

Nim reads like Python: indentation, few symbols, type inference, uniform call syntax. It checks like Ada: distinct types, range types, effects, exhaustive case. There is one main way to build. That makes it light to read, which matters for humans maintaining code and for agents writing it: a strict compiler with clear errors is the best reviewer an agent can get. Every experiment in the lab table was built with an agent, spec first, in a few days.

Models have seen far less Nim than Python or Rust: they drift to old APIs and invent procs. Specs, tests and a fast compiler catch it, but the friction is real.
CAPCOMThe crew

A language is its people. A web browser from scratch, e-ink photo frames, a kernel tutorial, a game on Steam, an Ethereum client. And the whimsical: a wordoku you play by dragging tiles, a CAD drawn for one wall of one flat, animated explainers, a notebook library that writes pages like this one.

A small community with a short bench: when a key maintainer gets busy, a library stops. Package tooling (nimble, atlas) has been in flux.

Nim as a language for agent-written code. Low cognitive load, a strict and fast compiler, macros that keep code short, and what happened when the lab projects were built that way: what agents get right and wrong in Nim.

Very topical, with first-hand data.

Fly A, the go/no-go poll, and borrow from the others:

Title
All Systems Nim
Subtitle
A go/no-go poll for a systems language with a low cognitive load
Track
Open Source Systems Languages
Duration
25 minutes
Abstract

"Cabin pressure go. Fuel system go. Oxygen go. All systems go." Before a launch, mission control polls every console, and each one answers go or no-go. This talk runs the same poll on Nim.

Nim is an open source systems language that compiles to C, C++, Objective-C and JavaScript. It reads like Python, frees memory with deterministic destructors, and has macros that run inside the compiler. People have written kernels, a web browser from scratch, e-ink display frameworks, firmware, GUIs, games and an Ethereum client in it. It is also a language where a whimsical idea becomes a working tool in a weekend, with a human or a coding agent at the keyboard.

We poll eight consoles, one capability each: bare metal, memory, metaprogramming, backends, interop, the compiler as a platform, cognitive load and the crew. Each answers with an example from the community and one from my recent experiments: a Polars dataframe library that calls Rust through its C ABI, Polars plugins written in Nim that Python loads, a REPL built on hot code reloading and incremental compilation, a furniture CAD with a 3D viewer in the browser, and a word puzzle game. Where Nim is not ready, we call a hold and say why.

Along the way we ask what makes a language a systems language, and why a low cognitive load is a systems property, for humans and agents alike.

Description

No Nim knowledge is needed: the examples read like Python. The talk is for people who build systems in any language and want to know what is different about Nim, and for Nim users looking for arguments.

Outline (25 minutes):
1. T-minus (3 min): the Freedom 7 checks; what is a systems language, from Ousterhout's 1998 split between system and scripting languages to Nim's aim of being efficient, expressive and elegant.
2. The poll (18 min): eight consoles, each a capability with a community example, an example of mine and a verdict.
- Bare metal: compiling through C, no runtime; kernels, microcontrollers, a handheld console.
- Memory: ORC, move semantics and destructors; a Nim library owning objects on the Rust heap.
- Metaprogramming: templates, macros and compile-time code; DSLs for dataframes and GUIs.
- Backends: one model drawn natively and in the browser.
- Interop: calling Rust through the C ABI; Nim plugins loaded by Python Polars.
- The compiler as a platform: hot code reloading and incremental compilation for a REPL; the next compiler, Nimony.
- Cognitive load: why it matters for people, and for coding agents.
- The crew: a browser from scratch, e-ink frames, games, and some whimsy.
3. Splashdown (2 min): the holds (ecosystem size, tooling, a compiler transition), and where to start.

Every example links to an open source repository and to a notebook page that explains it.

T-03 · ABORT MODESRisks and open questions

# ---------------------------------------------------------------- 4 what is a system
nbRawHtml: """<h2><span class="t">T-07 · SYSTEMS THINKING</span>What is a system, anyway?</h2>"""

nbText: """
The prompt for this talk asks it directly: *what is systems thinking, after all?* Three answers, each good for one slide.

**The 1998 split.** In "Scripting: Higher Level Programming for the 21st Century" (IEEE Computer, 1998), John Ousterhout
split languages in two: *system programming languages* (C, C++, Java), typed and compiled, for building data structures
and algorithms from scratch; and *scripting languages* (Tcl, Perl, Python), for gluing components together quickly.
You pick one side and pay its price. Most "non-mainstream systems languages" in this devroom are attempts to refuse
that choice. Nim's tagline says it plainly: a statically typed compiled systems language with concepts from Python,
Ada and Modula, aiming to be *efficient, expressive, elegant*.

**The systems-thinking definition.** Donella Meadows, in *Thinking in Systems*: a system is a set of elements, interconnected
so that together they achieve a purpose. Look at a language that way and the question changes. Not "can it touch
the metal?" but "how do its parts work together?" In Nim the macros, the type system, the destructors and the backends are
not separate features. A macro writes code the type checker checks, which the destructors manage, which any backend can emit.
`{.polarsExpr.}` in nanuq-more is a good example: one macro turns a plain Nim proc into a C ABI function with Arrow buffers,
and on the JS backend the same macro does nothing, so the module runs in a browser too.

**The human in the loop.** The part of a system people forget is the operator. Cognitive load is a systems property:
a language that fits in your head lets you hold more of the *rest* of the system in it. The 2026 version of this
argument has a new operator: the coding agent. A language with little syntax, one obvious way to build, readable code
and a fast, strict compiler gives an agent the same thing it gives a human: short feedback loops and fewer places to be wrong.
Most of the experiments above were written that way.

The talk's thesis, in one sentence:

> Nim is a systems language because its parts form a system: low-level control, a high ceiling and a low cognitive load,
> held together by a compiler you can program. That is why it is good at kernels **and** at word puzzles.
"""

  import std/[dom, math]

  let lamps = document.querySelectorAll(".lamp")
  let callout = document.getElementById("callout")

  proc say(html: string) = callout.innerHTML = html.cstring

  proc reset() =
    for i in 0 ..< lamps.len:
      lamps[i].classList.remove("go")
      lamps[i].classList.remove("hold")
      lamps[i].classList.remove("live")

  proc step(i: int) =
    if i > 0: lamps[i - 1].classList.remove("live")
    if i >= lamps.len:
      say("<span class=\"k\">FLIGHT:</span> All consoles report go.<br><span class=\"allgo\">All systems Nim.</span>")
      running = false
      return
    let lamp = lamps[i]
    lamp.classList.add("live")
    lamp.classList.add("go")
    say("<span class=\"k\">" & $lamp.getAttribute("data-code") & ":</span> " & $lamp.getAttribute("data-call") & " <b>Go.</b>")
    discard setTimeout(proc () = step(i + 1), 1300)

  document.getElementById("poll").addEventListener("click", proc (e: Event) =
    if running: return
    running = true
    reset()
    say("<span class=\"k\">FLIGHT:</span> All consoles, go/no-go for launch.")
    discard setTimeout(proc () = step(0), 900))

  # consoles that answer "go, with a hold" (see the holds in the console section)
  const holdCodes = ["EECOM", "FIDO", "RETRO", "INCO", "SURGEON", "CAPCOM"]
  document.getElementById("holds").addEventListener("click", proc (e: Event) =
    if running: return
    reset()
    for i in 0 ..< lamps.len:
      let code = $lamps[i].getAttribute("data-code")
      if code in holdCodes: lamps[i].classList.add("hold")
      else: lamps[i].classList.add("go")
    say("<span class=\"k\">FLIGHT:</span> Amber is go, with a hold: it works, with a caveat the talk names. Green is clean go."))
